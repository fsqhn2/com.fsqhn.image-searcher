### s-20261112-0858-c44f

- **用户给的**：原图有水印，愣是没读出来。
- **日志事实**：02:48 整图（1066×1600）读回 `Reng♡ @id.NaohingLax`，3.2 秒；同一秒写「重读水印：还是 @id，不重复核」；之后切六块花了 50 秒，读出 `MURUA`、`MIRUI`、`idcNothinglose`，一个都没核上。
- **根因**：取号正则 `@([A-Za-z0-9_]{2,15})` 遇 `.` 停，截成 `@id`；而 `@id` 之前试过，于是整条结果被丢弃。判定「重读还是它」只看第一个候选。
- **另一条线索**：机器人自带的「理解图片」把同一处读成 `水印"@id=NothingLee"`——图上是 `id=某某`，中文平台常用写法，取号函数完全不认。
- **修复**：认得 `id=` / `id:` / `id.` / `id：`（含等号被读成 `c` 的写法）；一条水印出多个候选、只跳过试过的；分块读从「整图之后」挪到「候选图之后」。

## 排查一单的顺序

1. 先看是按图缓存命中还是真跑了一遍（日志有「按图缓存命中」）。旧结论出现时，让用户重搜。
2. 看分流统计：`match` / 疑似 / 未验证各几条，`best` 是谁、来源是哪一步（指纹 / 视觉 / 水印 / identity）。
3. 看水印读数：整图读到什么、取号成什么、有没有去核。
4. 看各引擎错误：`summary.errors` 里的 HTTP 状态，Yandex 先怀疑线路，SerpAPI 先看是不是 429。
5. 看 Grok：`Grok 上游 5xx` 说明这条线这轮白跑，别把它的缺席当成插件判断失误。
6. 定位到具体函数后改，补一条单测，再在服务器上用同一张图重跑，看日志确认那一步真的执行了。
